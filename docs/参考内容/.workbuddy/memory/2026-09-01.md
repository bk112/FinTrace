## 对比目录下的 RL 奖励函数设计

对 `docs/参考内容/` 下两处材料的奖励函数做了横向对比，涉及四套设计：

- **Search-R1 默认版**（`Search-R1/verl/utils/reward_score/qa_em.py`，`main_ppo.py` 调用 `qa_em.compute_score_em`）
  纯 outcome 奖励：答案 EM 命中得 1.0，否则 0（format_score 默认 0）。extract_solution 有个反直觉实现——
  要求 `<answer>` 标签出现 ≥2 次才取最后一个匹配，否则返回 None，目的是跳过 prompt/模板里混入的假答案标签。

- **Search-R1 v0.3 格式变体**（`qa_em_format.py` + `scripts/nq_hotpotqa/v0.3/train_*_format.sh`，走 `main_ppo_format.py`）
  加了 `structure_format_score=0.2` / `final_format_score=0.1` / `retrieval_score`（默认 0）三档，
  用 `is_valid_sequence` 状态机校验 think→search→information→answer 顺序。仍是离散档位（1.0/0.8/0.3/0.2/0.1/0）。

- **端到端 Agentic RL**（文档 4.9 节，Qwen3-8B + slime + GRPO）
  五维加权 = 答案 F1×0.4 + CEM 0.2 + 格式 0.2（一票否决）+ 搜索激励 0.1（每次 +0.05，2 次封顶）+ 检索正确 0.1。
  核心思路是把 Search-R1 的二值 SubEM 稠密化成连续 F1，并补低门槛 CEM 信号。
  生成阶段 break 条件（>25 轮、重复 query、单轮工具调用 >5、标签解析错）直接判 0。

- **Planning RL**（文档 3.3 节，Qwen3-32B + verl）
  无 ground truth 可比对，改用独立部署的 Qwen3-32B 作 LLM Judge，满分 100 = 格式 5（规则）+ 逻辑链 30（LLM 分级→规则扣分）+ Agent 选择 65（Planning/Execute 分层判据）。
  要点：LLM 只做"问题等级分类"不直接打分，减少波动；调用失败重试 3 次后降级而非给 0。

### 结论要点
Search-R1 = 最小干预（outcome-only，靠 RL 自然涌现）；文档方案 = 主动稠密塑形（补 CEM、搜索激励、检索正确、终止惩罚）。
根本差异在**奖励信号是否可客观验证**：Agentic 能在真实检索环境拿到客观结果信号，Planning 只能靠 LLM Judge 间接评分，故 RL 提升幅度有限。
